**Location:** `algebra.rs:145-165`

```rust

    // SECURITY: Converting field elements to strings and parsing is
    // timing-dependent and could leak information.
    let coeff_str = coeff.to_string();
    if let Ok(val) = coeff_str.parse::<u128>() {
        // Variable-time operations on secret data
    }

```

**Issue:** String conversion and parsing introduce timing channels that could leak polynomial coefficients.

**Attack Scenario:**
1. Attacker measures time for `estimate_noise()` calls
2. Different coefficient values take different parsing times
3. Attacker reconstructs polynomial structure from timing measurements

**Impact:** 
- Can leak secret polynomial coefficients
- Compromises forward secrecy
- Real-world exploitability: MEDIUM (requires local access + precision timing)

**Fix Priority:** HIGH - Fix within 2 weeks

**Recommended Solution:**


### H2. Field Element String Conversion in `extract()` 🟠

**Location:** `multilinear.rs:78-84`

```rust
for coeff in encoding.value.coeffs() {
    let coeff_str = coeff.to_string();
    let bytes = coeff_str.as_bytes();
    input_key_material.extend_from_slice(bytes);
}
```

**Issue:** Non-deterministic and timing-dependent serialization for cryptographic key material.

**Problems:**
1. String representation is implementation-dependent
2. Not constant-time
3. May leak coefficient information via timing
4. Inefficient (string allocation for every coefficient)

**Impact:**
- Side-channel leakage during key extraction
- Non-deterministic keys (different string formats → different keys)
- Performance degradation

**Fix Priority:** HIGH - Fix within 2 weeks

**Recommended Solution:**

```rust
pub fn extract(&self, encoding: &Encoding<F>) -> Result<Vec<u8>, Box<dyn std::error::Error>> {
    use ark_serialize::CanonicalSerialize;
    
    // Pre-allocate for deterministic serialization
    let mut input_key_material = Vec::with_capacity(encoding.value.coeffs().len() * 32);
    
    // Use canonical, constant-time serialization
    for coeff in encoding.value.coeffs() {
        let mut coeff_bytes = Vec::new();
        coeff.serialize_uncompressed(&mut coeff_bytes)
            .map_err(|e| format!("Serialization failed: {}", e))?;
        input_key_material.extend_from_slice(&coeff_bytes);
    }
    
    // SECURITY: HKDF key derivation provides forward secrecy
    let hkdf = Hkdf::<Sha3_256>::new(None, &input_key_material);
    let mut output_key_material = [0u8; crypto::HKDF_OUTPUT_SIZE];
    
    hkdf.expand(b"multilinear-key-v1", &mut output_key_material)
        .map_err(|e| format!("HKDF expansion failed: {:?}", e))?;
    
    Ok(output_key_material.to_vec())
}
```

### H4. Race Condition in Group ID Generation 🟠

**Location:** `lib.rs:176-195`

```rust
fn generate_secure_group_id() -> Result<GroupId, HPairError> {
    let cache = IN_MEMORY_CACHE.lock()...
    if !cache.contains_key(&group_id) && STORAGE.load_group(group_id).is_err() {
        return Ok(group_id);
    }
}
```

**Issue:** TOCTOU (Time-Of-Check-Time-Of-Use) race between checking and inserting.

**Attack Scenario:**
1. Thread A generates ID X, checks it's available
2. Thread B generates same ID X, checks it's available (between A's check and insert)
3. Both threads proceed with same group ID
4. Group state corruption

**Probability:** Low but non-zero with high concurrency

**Fix Priority:** HIGH - Fix within 2 weeks

**Recommended Solution:**

```rust
fn generate_secure_group_id() -> Result<GroupId, HPairError> {
    let mut attempts = 0;
    
    while attempts < api::MAX_GROUP_ID_ATTEMPTS {
        let mut id_bytes = [0u8; 8];
        OsRng.fill_bytes(&mut id_bytes);
        let group_id = u64::from_le_bytes(id_bytes);
        
        if group_id == 0 {
            attempts += 1;
            continue;
        }
        
        // Atomic check-and-insert
        static IN_MEMORY_CACHE: Lazy<Mutex<HashMap<GroupId, Arc<Mutex<GroupState>>>>> =
            Lazy::new(|| Mutex::new(HashMap::new()));
            
        let mut cache = IN_MEMORY_CACHE.lock()
            .map_err(|_| HPairError::InternalError("Cache lock poisoned".to_string()))?;
        
        // Double-check in same critical section
        if !cache.contains_key(&group_id) && STORAGE.load_group(group_id).is_err() {
            // Reserve the ID immediately
            cache.insert(group_id, Arc::new(Mutex::new(
                // Use placeholder state that will be updated
                create_placeholder_state()
            )));
            return Ok(group_id);
        }
        
        attempts += 1;
    }
    
    Err(HPairError::InternalError("Could not generate unique group ID".to_string()))
}
```

### M1. Incomplete Constant-Time Implementation 🟡

**Location:** `constant_time.rs`

**Issue:** Module provides constant-time primitives but they're not consistently used.

**Examples:**
- `ct_coeff_access()` just wraps `safe_array_access()` (not constant-time)
- `ct_in_range()` has timing-dependent branching
- No constant-time conditional moves for field elements

**Impact:** Partial protection, false sense of security

**Fix Priority:** MEDIUM - Fix in next sprint (1 month)

**Recommended Solution:**

```rust
/// Truly constant-time coefficient access using subtle crate
pub fn ct_coeff_access<F: ConditionallySelectable>(
    coeffs: &[F], 
    index: usize
) -> Option<F> where F: Copy + Default {
    let len = coeffs.len();
    
    if index >= len {
        return None;
    }
    
    // Constant-time selection
    let mut result = F::default();
    for (i, &coeff) in coeffs.iter().enumerate() {
        let choice = Choice::from(if i == index { 1 } else { 0 });
        result = F::conditional_select(&result, &coeff, choice);
    }
    
    Some(result)
}

/// Constant-time range check without branching
pub fn ct_in_range(value: u64, min: u64, max: u64) -> Choice {
    let ge_min = value.wrapping_sub(min).ct_eq(&value.saturating_sub(min));
    let le_max = max.wrapping_sub(value).ct_eq(&max.saturating_sub(value));
    ge_min & le_max
}
```

**Location:** `lib.rs:142-175`

**Issue:** No protection against rapid group creation spam.

**Attack Scenario:**
1. Attacker creates 10,000 groups rapidly
2. Fills MAX_GROUPS limit
3. Legitimate users can't create groups
4. DoS attack

**Fix Priority:** MEDIUM - Fix in next sprint

**Recommended Solution:**

```rust
use std::collections::VecDeque;
use std::time::Instant;

struct RateLimiter {
    requests: VecDeque<Instant>,
    max_requests: usize,
    window: Duration,
}

impl RateLimiter {
    fn check_rate_limit(&mut self) -> bool {
        let now = Instant::now();
        
        // Remove old requests
        while let Some(&oldest) = self.requests.front() {
            if now.duration_since(oldest) > self.window {
                self.requests.pop_front();
            } else {
                break;
            }
        }
        
        // Check limit
        if self.requests.len() >= self.max_requests {
            return false;
        }
        
        self.requests.push_back(now);
        true
    }
}

// Global rate limiter: 10 groups per minute
static RATE_LIMITER: Lazy<Mutex<RateLimiter>> = Lazy::new(|| {
    Mutex::new(RateLimiter {
        requests: VecDeque::new(),
        max_requests: 10,
        window: Duration::from_secs(60),
```
